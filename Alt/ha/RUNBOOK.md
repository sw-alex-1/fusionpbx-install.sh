# RUNBOOK — рабочая инструкция HA-кластера FusionPBX (Alt/ha)

> Назначение: «прошло полгода, нода упала, никто ничего не помнит».
> Каждый раздел самодостаточен: симптом → что происходит само → что делать
> тебе → как убедиться, что всё хорошо. Теория и обоснования — в
> [DESIGN.md](DESIGN.md); здесь только действия.
>
> **Статус:** команды соответствуют реализованному CLI (DESIGN.md v0.3).
> Скрипт `fusionpbx-ha.sh` написан и покрыт тестами песочницы; до прохождения
> стенда 3×ALT (DESIGN.md §15.3) считайте развертывание экспериментальным.
> При изменениях CLI документ правится вместе с DESIGN.md.

## Карта кластера и мини-словарь

```
VM1 (data)    = FusionPBX + PostgreSQL primary + repmgrd + haproxy + lsyncd
VM2 (data)    = FusionPBX + PostgreSQL standby + repmgrd + haproxy + lsyncd
VM3 (witness) = крошечная PostgreSQL (только метаданные кластера) + repmgrd
```

- **primary / standby** — роли PostgreSQL; после отказа они меняются местами
  автоматически. Кто сейчас кто — показывает `--status`.
- **witness** — третий голос при принятии решения о failover; пользовательские
  данные не хранит никогда.
- **127.0.0.1:5433** — единственная точка записи в БД: haproxy на каждой
  data-ноде сам ведёт к текущей primary. Приложения и FreeSWITCH других адресов
  БД не знают.
- **Токен** — одноразовая строка для вступления ноды в кластер; содержит
  секреты, обращаться как с root-паролем.
- Медиа-файлы (записи разговоров, voicemail, факсы) зеркалируются между VM1 и
  VM2 через lsyncd автоматически.

Все команды ниже выполняются от root в каталоге `Alt` клона репозитория (с 0.3.34 скрипт
`fusionpbx-ha.sh` лежит рядом с `pre-install.sh`/`install.sh` слоя 1 — одна система,
одно место; его ресурсы и документация остались в `Alt/ha/`; пример ниже
предполагает стандартный путь слоя 1; у тебя может быть другой):

```sh
cd /usr/src/fusionpbx-install.sh/Alt
```

## 1. Развёртывание с нуля

Исходное состояние: 3 чистые VM на **трёх разных** хостах Proxmox, статические
IP, NTP работает на всех трёх. На VM3 установщик FusionPBX (слой 1) НЕ ставится
вообще — только команды из этого каталога.

Один раз, до всего: **настроить АТС на VM1** (домены, расширения, пользователей,
маршруты). Всё, что настроено на VM2 до кластеризации, будет стёрто: база VM2
заменяется копией с VM1.

### Шаг A — VM1 и VM2: обычная одиночная установка (слой 1)

```sh
# в корне клона репозитория, на VM1 и на VM2 по отдельности:
./pre-install.sh
./install.sh
```

**Что происходит:** ставится одиночный FusionPBX (Angie + php-fpm + FreeSWITCH
+ PostgreSQL) с локальной базой. Никаких кластерных компонентов. Подробности и
опции — в README корня репозитория. Повторный запуск безопасен: защита от
повторного запуска не даст уничтожить настроенную систему.

### Шаг B — VM1: инициализация кластера

```sh
cd Alt/ha
./fusionpbx-ha.sh --init --node2 <IP-VM2> --node3 <IP-VM3>
```

**Что происходит:** локальная база VM1 объявляется primary кластера. Ставятся
repmgr/haproxy/lsyncd, конфигурируются (включая `/etc/hosts` на все три ноды),
FusionPBX и FreeSWITCH переключаются на запись через `127.0.0.1:5433`.
Печатается **токен** — перепиши его в надёжное место (секрет!); на VM2 и
VM3 он вводится строкой или файлом (`--join @файл`). Скрипт уходит в
ожидание двух остальных нод; АТС при этом продолжает работать. Сначала
выполнится быстрый рестарт PostgreSQL (шаг wal-log-hints — включает журнал,
нужный для ремонта бывшей primary).

### Шаг C — VM2 и VM3: вступить в кластер

```sh
# на VM2 и на VM3 (порядок любой, можно параллельно), в Alt/ha клона репозитория:
./fusionpbx-ha.sh --join <ТОКЕН>
```

**Что происходит:** роль определяется автоматически по собственному IP:
VM2 → standby, VM3 → witness. На VM2 локальная база **стирается и заменяется
физической копией с VM1** (скрипт спросит подтверждение), затем включается
стриминг-репликация и до-зеркалируются медиа-файлы. На VM3 разворачивается
крошечная PostgreSQL с метаданными repmgr. Ничего вводить на VM1 больше не
нужно: её скрипт сам увидит обе ноды и включит синхронную репликацию
(RPO = 0).

### Шаг D — финальная проверка

```sh
./fusionpbx-ha.sh --status    # на VM1: primary + standby + witness, лаг ≈ 0
./fusionpbx-ha.sh --doctor    # на всех трёх: код выхода 0 = здоровы
```

Токен после этого больше не нужен (cluster.conf уже на всех нодах). Забыл
сохранить / нужно переиздать: `--print-token` на VM1.

### Веб-интерфейс: домен FusionPBX и вход на standby (0.3.20)

Слой 1 создаёт домен FusionPBX из `domain_name=ip_address`
(`resources/config.sh`) — то есть **домен в БД = IP той ноды, где ставили
слой 1 первично** (у нас — IP primary). Аутентификация FusionPBX
привязана к домену (Host-заголовок сверяется с `v_domains`, пользователь
живёт в своём домене). Поэтому:

* `https://<IP primary>` — вход работает (Host совпадает с доменом);
* `https://<IP standby>` — «Incorrect Username or Password»: IP standby
  не является доменом, а свой домен (и свой admin от layer 1) standby
  потерял вместе с локальной БД — её заменил клон primary (join, шаг 5).

Логин/пароль для UI на ЛЮБОЙ ноде — учётка primary (та, что layer 1
создал на VM1). Чтобы вход работал и по IP standby — добавьте IP standby
как **алиас домена**: UI primary → Settings → Domains → домен → Alias
(или SQL: `INSERT INTO v_domain_aliases (domain_alias_uuid, domain_uuid,
domain_alias_name, domain_alias_enabled) VALUES (gen_random_uuid(),
'<domain_uuid>', '<IP standby>', 'true');`). Более правильный
операционно вариант — ходить на кластер по одному DNS-имени (оно же
домен), а не по IP нод.

## 2. Проверка здоровья (регулярная)

```sh
./fusionpbx-ha.sh --status    # компактная сводка прямо сейчас
./fusionpbx-ha.sh --doctor    # полный чек-лист; exit 0 = всё хорошо
```

**Норма:** одна нода primary, одна standby в состоянии streaming с
`sync_state = sync` и лагом ≈ 0; witness виден как running; lsyncd активен и
без ошибок; время синхронизировано. `--doctor` уместно поставить в
мониторинг: ненулевой код выхода = авария (внутри сводки будет причина).
С 0.3.34 doctor дополнительно проверяет **кворум-линки** — аутентификацию
repmgr до всех трёх нод (psql через `.pgpass`) и полноту самого `.pgpass`:
именно сломанная аутентификация к witness 27.10 осталась незамеченной
(TCP-проверка говорила «reachable») и не дала standby повыситься при
отказе primary.

## 3. Упала data-нода (VM1 или VM2)

Сначала выясни, кем она была:

```sh
./fusionpbx-ha.sh --status    # на любой живой ноде
```

### 3а. Упала standby

Звонки, веб, записи живут как раньше; кластер остался без резерва.
Автоматического восстановления нет: ноду возвращает `--repair` (§5).

Если standby задерживается надолго, запись на primary надо перевести в
async (иначе коммиты ждут пропавший sync-standby): запусти `--repair` на
surviving primary — она сама снимет sync-имена и подтвердит, что запись
работает; `--doctor` при этом показывает «async mode» (не авария, а
деградация). При возврате standby `--repair` на нём вернёт sync (RPO = 0).

### 3б. Упала primary

**Автоматика (30–45 секунд):** repmgrd на standby сверяется с witness → standby
повышается до primary → haproxy переключает запись на неё → телефоны
перерегистрируются на выжившую ноду. От оператора на этапе аварии ничего не
требуется; текущие звонки через упавшую ноду оборвутся.

**Если standby НЕ повышается, а ждёт (урок стенда, 27.10 / 0.3.34).**
Симптом: primary выключили, а на standby в `--status` всё ещё standby,
entry point не отвечает, FreeSWITCH сыплет `The sql server is not responding`;
в `/var/log/repmgr/repmgrd.log` при этом:

```
connection to server at "192.168.1.238", port 5432 failed: fe_sendauth: no password supplied
NOTICE: unable to reach a qualified majority of nodes
NOTICE: election cancelled
DETAIL: node will enter degraded monitoring state waiting for reconnect
```

Это сломанная **аутентификация кворума**: до 0.3.34 `.pgpass` на data-нодах
не содержал строки witness (а на самом witness — строки самого себя), и
после уборки паролей из conninfo (0.3.33) standby не мог залогиниться к
witness для подсчёта большинства — ждал весь инцидент вместо промоушена.
Лечение: обновить скрипты на всех нодах (§7), затем `--repair` на всех
трёх (каждая нода перепишет свой `.pgpass`); после этого `--doctor`
показывает `quorum link to ... authenticated` для всех трёх нод. Если
witness просто выключен — это другой случай (§4, WARN без аварии).
Включенная нода-бывшая primary вернётся сама: boot guard видит
«peer in recovery» и разрешает старт, node2 реконнектится к ней без
ремонта (первые записи на вернувшейся primary могут подвиснуть на
несколько секунд — sync-имя ждёт переподключения standby).

**Предусловие (урок стенда, 0.3.21):** автоматика работает, только пока
`repmgr` АКТИВЕН на выживающей ноде — это единственный, кто промоутит
standby. На стенде hard-off primary пережила нода с остановленным repmgrd
(след незавершённого `--repair`, который останавливает repmgrd/lsyncd на
шаге 2 и поднимает на шаге 4): промоута не было, haproxy честно не пускал
трафик к standby (агент 503), всё стояло до возврата primary. Проверка
перед тестом/аварией: `systemctl is-active repmgr` (или зелёный
`--doctor`). С 0.3.21 юнит-дроп-ин даёт repmgrd `Restart=always` (и
lsyncd `Restart=on-failure`) — умерший демон возвращается через 10 секунд;
осознанный `systemctl stop` (установочные потоки) по-прежнему уважается.

**Приложения (урок стенда, 0.3.24):** промоут — это ещё не конец failover.
При ЖЁСТКОМ выключении primary (без RST по TCP) локальные приложения —
php-fpm и FreeSWITCH на выжившей ноде — сидят на сокетах к мёртвому пиру
и молча ретранслируют до ~15–30 минут (`tcp_retries2`): на стенде это
выглядело как бесконечное ожидание веб-интерфейса и «sip: авторизация»
на телефоне — при полностью рабочем новом primary (промоут за ~30с,
haproxy маршрутизирует, entry point 5433 отвечает учёткой fusionpbx).
С 0.3.24 promote.sh после успешного промоута сам перезапускает локальные
php-fpm/angie/FreeSWITCH (`try-restart` через sudoers) — сокеты к мёртвому
пиру сбрасываются, приложения переподключаются к 127.0.0.1:5433. Если
нода с промоутом ДО 0.3.24 (или что-то всё ещё висит) — перезапусти их
руками: `systemctl restart php8.3-fpm angie freeswitch`; телефон после
неудачных попыток уходит в паузу между попытками — перерегистрируй его
принудительно (перезагрузка телефона / вкл-выкл учётки) или подожди
следующего цикла.

**«could not restart» в repmgrd.log на повышенной ноде (урок стенда,
27.10 13:57 / 0.3.35):** после промоута node2 promote.sh НЕ перезапустил
приложения — все три `sudo -n systemctl try-restart` умерли мгновенно и
МОЛЧА (вывод глотался). При этом сами sudo-правила корректны, а из
ремонтных сессий тот же sudo работает — падал ровно контекст ЮНИТА
repmgrd (главные подозреваемые: systemd-харденинг стокового юнита
`NoNewPrivileges` — под ним setuid игнорируется — и/или файл RPM
`/etc/sudoers.d/repmgr`, читаемый ПОСЛЕ нашего). С 0.3.35: promote.sh
печатает первую строку ошибки (причина видна в repmgrd.log), юнит-дроп-ин
отключает `NoNewPrivileges` (с верификацией), а каждый `--repair`
проверяет sudo-путь пробой `sudo -n -l`. Лечение на живой ноде:
обнови скрипты (§7) + `--repair` на ней (сходится дроп-ин и проверка),
а приложения перезапусти руками (команда выше). Диагностика, если
повторится: `grep 'could not restart' /var/log/repmgr/repmgrd.log`,
`runuser -u postgres -- sudo -n -l`, `cat /etc/sudoers.d/repmgr`,
`systemctl cat repmgr | grep -iE 'NoNewPriv|Protect'`.

**Read-only-зомби после холодной загрузки (урок стенда, 23.10 / 0.3.26):**
если после загрузки кластера FreeSWITCH на primary отказывает в записи
(`в транзакции в режиме "только чтение" нельзя выполнить UPDATE` в fs_cli,
например на update sip_subscriptions), при том что свежий коннект через
5433 той же учёткой пишет, — core-пул FS держит сессию, застрявшую в окне
загрузки на бэкенде, неспособном принимать записи; haproxy такую сессию
не убивал, а FS по ошибке запроса не реконнектится (сокет жив — сервер
отказывает в записи). Лечение: `systemctl restart freeswitch` на
пострадавшей ноде, телефон перерегистрировать принудительно. С 0.3.26
`on-marked-down shutdown-sessions` убивает такие сессии автоматически в
момент ухода бэкенда из ротации. Точное окно загрузки ищется журналами:
`journalctl -b -u haproxy --no-pager | grep -E 'UP|DOWN'`;
`journalctl -b -u fusionpbx-ha-agent --no-pager`; на standby —
`select pid, client_addr, backend_start, state from pg_stat_activity
where datname='fusionpbx' and client_addr='<IP ноды с пострадавшим FS>'`
(долгоживущая сессия со временем старта ≈ загрузка = зомби); промоуты —
`repmgr -f /etc/repmgr/repmgr.conf cluster event --limit 20`.

**После аварии:** проверь `--status` на живой ноде (она теперь primary, witness
running), сделай пробный звонок. Упавшую ноду верни по §5 — она вернётся уже
standby; вернуть ей роль primary можно плановым `repmgr switchover` (когда всё
устаканилось, необязательно).

## 4. Упал witness (VM3)

**Кластер полностью работоспособен**: звонки, запись, веб, репликация — всё
как было. Деградация одна: **автоматический failover отключён** — если теперь
упадёт primary, standby не соберёт кворум и останется ждать (см. §6). Поэтому
чинить без спешки, но и не откладывать: `--doctor` будет напоминать.

Ремонт: поднять VM (или пересобрать — §5) и на ней:

```sh
./fusionpbx-ha.sh --repair    # пересоздаёт крошечную PG и перерегистрирует witness
```

**Witness «доступен», но кворум сломан (0.3.34).** До 0.3.34 `.pgpass` на
data-нодах не содержал строки witness: TCP-проверка говорила «reachable»,
а аутентификация repmgr падала (`fe_sendauth: no password supplied`) — при
отказе primary standby не мог собрать кворум (§3б). `--doctor` 0.3.34
проверяет именно аутентификацию (`quorum link to ... authenticated`);
лечение то же: обновить скрипты (§7) и `--repair` на всех трёх нодах.

## 5. Вернуть ноду в строй (`--repair`)

Когда: нода вернулась из отказа (§3), перезагрузилась, ей заменили диск, или
`--doctor` показывает проблемы репликации. Токен не нужен — вся информация о
кластере уже в `/etc/fusionpbx-ha/cluster.conf` на самой ноде.

**С 0.3.27 жёстко упавшая primary больше НЕ грузится competing- primary:**
boot guard (ExecStartPre у postgresql.service на дата-нодах) при загрузке
спрашивает пира: если его агент/БД подтверждают живую primary — локальный
PostgreSQL не стартует вовсе (журнал: `journalctl -b -u postgresql`,
«refusing to start a competing primary … run fusionpbx-ha.sh --repair»).
Это безопасное состояние: веб и телефония ЭТОЙ ноды продолжают работать —
её haproxy маршрутизирует на выжившую primary. Не запускай PostgreSQL
вручную — просто выполни `--repair` ниже (с 0.3.28 ремонт проходит guard
без помех: свой классификационный старт он помечает флагом в `/run`,
который guard пропускает, а флаг не переживает перезагрузку). Standby
(standby.signal) и непроклонированная нода грузятся как раньше, без
задержек; единственная цена — до ~30 с ожидания, если пир вообще не
отвечает (одновременная загрузка всего кластера / единственная выжившая
нода).

**С 0.3.29 возврат упавшей primary автоматический** (когда это безопасно):
на каждой загрузке дата-ноды юнит `fusionpbx-ha-auto-rejoin` повторяет
вердикт guard'а и, если пир подтверждённо живая primary, сам выполняет
rejoin с pg_rewind (та же механика, что `--repair` на шаге 3), вводит
ноду standby'ем, поднимает repmgrd/lsyncd и возвращает синхронный режим
на primary — без администратора. Автоматика ОТКАЗЫВАЕТСЯ (PostgreSQL
остаётся лежать — то же безопасное состояние, приложения работают через
пир; причина в `journalctl -b -u fusionpbx-ha-auto-rejoin`), если:
- таймлайны не сходятся: пир не ответвился именно от нашего таймлайна,
  или наш таймлайн ≥ пикового — у нас может быть WAL, которого нет у
  пира (многофайловерные/экзотические топологии — решать человеку);
- точка расхождения дальше ~128 МБ WAL (настраивается) — похоже на
  записи, сделанные при сетевем разделе в async-режиме: авто-перемотка
  могла бы их съесть, `--repair` решает человек;
- локальная база не «бывшая primary» (повреждена / экс-standby без
  сигнала) или rejoin дважды упал (при этом в журнал автоматически
  пишется `pg_rewind --debug` — реальный дебаг перемотки, если она
  действительно падает; до 0.3.30 сама обёртка repmgr умирала раньше
  pg_rewind — врезка про TMPDIR ниже).
Никогда автоматически: force-clone (вайп данных без человека недопустим)
и промоут. Одна попытка на загрузку; следующая загрузка retry'ит.

**Если авто-rejoin провалился наполовину (урок стенда, 27.10 14:0x / 0.3.35):**
rejoin может умереть ПОСЛЕ того, как repmgr уже поднял PostgreSQL —
нода остаётся «зомби-стендбаем»: PG работает в recovery на новом
таймлайне, но запись в метаданных всё ещё «primary» → repmgrd честно
отказывается стартовать («node is registered as a primary but running as
a standby», рестарт-луп каждые 10с), а `--status` показывает «! running as
standby». С 0.3.35 авто-rejoin на провале различает два остатка
по WAL-ресиверу: если нода ПОДКЛЮЧЕНА к пиру и догоняет — она остаётся
работать (догонка ценна, `--repair` доведёт запись метаданных без
разрыва репликации); если НЕ подключена — PG и repmgrd ОСТАНАВЛИВАЮТСЯ
(безопасное состояние: приложения этой ноды работают через пир,
расходящийся WAL больше не проигрывается поверх перемотанных файлов;
следующая загрузка повторит rejoin). В обоих случаях лечение одно:

```sh
./fusionpbx-ha.sh --repair    # классифицирует, перемотает если нужно,
                             # обновит запись, поднимет repmgrd и sync
```

```sh
./fusionpbx-ha.sh --repair                  # обычный случай: данные на диске уцелели
./fusionpbx-ha.sh --repair --force-clone    # PGDATA мусор / новый диск: полная переклонировка
```

**Что происходит (0.3.25):** сначала останавливаются lsyncd → repmgrd, затем
ремонт КЛАССИФИЦИРУЕТ локальную базу (для чего на миг поднимает её —
guard 0.3.27+ пропускает именно этот старт, 0.3.28; с 0.3.32, если PG
вообще не поднимается — например, «зомби» с контрольной точкой за
точкой ответвления таймлайна primary, такой стендбай PG16 отказывается
грузить в принципе — узел автоматически считается разошедшимся и идёт
сразу в rejoin с pg_rewind: `--force-clone` остался фолбэком только
для реально повреждённого PGDATA). Если это здоровый
standby, уже стримящий с текущей primary (типично после простого
сбоя/перезагрузки; с 0.3.31 «стримящий» подтверждает сама primary —
`pg_stat_replication` видит наш application_name в `state='streaming'`,
либо replay видимо продвигается в догонке) —
rejoin не выполняется вовсе: репликация не прерывается, обновляется только
запись в метаданных, сервисы поднимаются. Если база разошлась (бывшая
primary после failover, standby на мёртвом/чужом upstream) — PostgreSQL
останавливается и выравнивается с текущей primary: быстрая перемотка
(pg_rewind, секунды-минуты) либо полный re-clone (`--force-clone`, минуты,
зависит от размера базы и диска); нода вводится как standby; медиа-файлы
досылаются с соседа **до** включения синка (защита от стирания зеркала
пустым каталогом; с 0.3.23 seed при занятой rrsync-блокировке соседа сам
ждёт и повторяет попытки — см. §9); сервисы поднимаются. Бывшая primary
после failover возвращается тем же способом — pg_rewind откатит её к общей
точке. Rejoin подключается к пиру явно от имени роли repmgr и к базе
repmgr (0.3.25: с голым `-h` repmgr уходил в базу `postgres` и падал
«relation "repmgr.nodes" не существует» — если видишь эту ошибку на шаге 3,
на ноде скрипт старой версии: `git pull` (§7) и повтори ту же команду,
завершённые шаги пропустятся).

**До 0.3.30 rejoin падал «unable to open temporary file» — это была не
ошибка pg_rewind.** Сообщение печатает сам repmgr, когда его обёртка
запуска команд не может создать временный файл для захвата stderr:
root-сессия SSH на ALT получает приватный TMPDIR от pam_mktemp
(`/tmp/.private/root`, режим 0700), `runuser` пробрасывает среду — и
repmgr, работая уже от postgres, пытался создать файл ВНУТРИ чужого
0700-каталога → отказ → rejoin умирал, даже не запустив pg_rewind (22.10
и 26.10, оба раза из ручного `--repair` по SSH; автоперезапуск ноды в
это не попадал — у systemd-юнитов нет PAM). С 0.3.30 каждый запуск
repmgr от postgres принудительно получает `TMPDIR=/tmp` (`repmgr_cmd` и
`pg-auto-rejoin.sh`): pg_rewind наконец выполняется, и при настоящем
отказе перемотки её полный вывод виден целиком.

**До 0.3.31 первый же реальный pg_rewind умирал «нет доступа к функции
pg_ls_dir».** У роли repmgr не было EXECUTE на файловые функции
pg_catalog, которыми pg_rewind собирает список файлов источника и читает
блоки (в grant-списке инсталлера их просто не было — до 0.3.30 pg_rewind
никогда не выполнялся, дыра была замаскирована). С 0.3.31 гранты
выдаются одним DO-блоком по ВСЕМ перегрузкам (pg_ls_dir, pg_stat_file,
pg_read_file, pg_read_binary_file, …) при каждом register-prelude на
primary и уходят на standby репликацией сами. На развёрнутом стенде:
`git pull` + любой `--repair`/register-прогон на primary. Смежный
симптом (состояние после неудачного rejoin, PostgreSQL поднялся
«стендбаем», но догнать не может НИКОГДА — собственный WAL ноды прокручен
за точку ответвления нового таймлайна primary): лаг не сходит, sync на
primary не включается («no streaming standby»), а `--repair` до 0.3.31
говорил «already a healthy standby» и скипал лечение; repair 0.3.31
распознаёт такое состояние (пир не подтверждает стриминг + replay
не движется) и перематывает pg_rewind'ом.

**До 0.3.33 rejoin мог умереть «unable to start server» БЕЗ объяснений.**
pg_rewind выполнялся корректно (в логе это видно по «0 files copied» при
крошечном расхождении), но старт сервера ВНУТРИ rejoin падал — а repmgr
при провале команды печатает только эту строку: вывод systemctl, вердикт
guard'а и FATAL postgres он выбрасывает (проверено по исходникам
repmgr 5.5.0). Наиболее вероятная причина — start-rate лимит systemd
(«Start request repeated too quickly»): классификационный старт этого же
прогона крутил crash-loop на ещё не перемотанных данных, и каждое падение
засчитывалось; у перемотанной базы шанса загрузиться так и не было. С 0.3.33
ремонт: (1) снимает rate-лимит перед rejoin и перед повторной попыткой
(`systemctl reset-failed`), (2) держит флаг guard на всё окно rejoin (его
внутренний `systemctl start` стартует БЕЗ guard-проверки), (3) ДО rejoin
проверяет sudo-путь (`sudo -n systemctl show postgresql` от postgres —
если sudoers/requiretty сломаны, умрёт адресное сообщение, а не глухой
«unable to start server»), (4) при любом провале печатает форензику прямо
в вывод: последние 40 строк `journalctl -u postgresql` + хвост лога
PostgreSQL + наличие standby.signal — если rejoin снова упадёт, причина
будет в консоли, её не придётся искать. Повторная попытка rejoin
автоматическая (pg_rewind можно запускать повторно).

**Пароли в логах (0.3.33).** Раньше пароль repmgr печатался открытым
текстом в WARNING-строках ping и в DETAIL «pg_rewind command is ...» —
repmgr выводит conninfo дословно, а пароль там лежал с самой первой
установки (и в repmgr.conf, и в записях метаданных). Теперь conninfo
без пароля (аутентификация — через `.pgpass` пользователя postgres,
режим 600), а устаревшие записи в `repmgr.nodes`/`repmgr.events`
вычищаются автоматически после каждой регистрации/rejoin (БД
реплицируется — чистка primary лечит все копии; witness перезаберёт
записи при следующем register --force). Старые файлы логов не
переписываются задним числом; разовая чистка руками:

```sh
sed -i -E 's/password=[^ ]*/password=***/g' /var/log/repmgr/repmgrd.log
# журнал systemd (binary) — ротация сама унесёт; немедленно:
journalctl --rotate --vacuum-time=2h   # удалит и последние 2 часа записей
```

**Кворум и `.pgpass` (0.3.34 — урок 27.10).** С 0.3.33 (пароли убраны из
conninfo) `.pgpass` пользователя postgres — единственный носитель пароля
для ВСЕХ подключений repmgr/repmgrd. 27.10 выяснилось, что файл data-нод
не содержал строки witness (а файл witness — строки самого себя): при
жёстком выключении primary standby честно обнаружил отказ, но подсчёт
кворума умер на аутентификации к witness («fe_sendauth: no password
supplied» → «unable to reach a qualified majority of nodes») — degraded
monitoring вместо промоушена, кластер лежал весь инцидент. С 0.3.34
`ha_write_pgpass` пишет строку witness в обеих ролях, а `--doctor`
проверяет и аутентификацию до всех трёх нод (4b), и полноту файла (4c).
На развёрнутом стенде достаточно обновить скрипты (§7) и прогнать
`--repair` на всех трёх нодах — prelude на каждой перепишет `.pgpass`;
регистрация witness заодно заберёт вычищенные записи метаданных.

`--repair` на ЗДОРОВОЙ ноде безопасен: прерывать стриминг он не будет
(именно этим путём чинятся остановленные сервисы и юнит-дроп-ины после
прерванного ремонта — просто запусти ту же команду ещё раз, завершённые
шаги пропускаются).

**Если нода пересобрана с нуля** (новая ОС, клона репозитория нет,
`/etc/fusionpbx-ha/` пуст): это не `--repair`, а `--join`:

```sh
# data-нода (VM1/VM2): сначала одиночная установка слоем 1 (см. §1, шаг A), затем:
./fusionpbx-ha.sh --join <ТОКЕН>
# witness (VM3): слой 1 не нужен, сразу:
./fusionpbx-ha.sh --join <ТОКЕН>
```

Токен: `--print-token` на VM1 — узле, где выполнялся `--init` (DESIGN.md §6.2).
Сохраняй токен заранее (парольный менеджер): он нужен при пересборке любой
ноды с нуля (§5), а переиздать его после потери VM1 без пересборки кластера
нельзя. Для ремонта живых нод (`--repair`) токен не нужен никогда.

**Проверка после ремонта:** `--doctor` на отремонтированной ноде + `--status`
на primary: нода видна, streaming, лаг тает до 0, lsyncd без ошибок.

## 6. Заморозка кластера (двойной отказ) — читать до действий

Симптом: отказали **две** ноды из трёх (любые). Оставшаяся data-нода
останавливает запись в БД: веб-интерфейс висит на сохранении, новые звонки не
оформляются. Голосовая часть ещё может работать по уже загруженной конфигурации.

**Это правильное поведение, а не сбой:** продолжать писать мог бы только
кластер без защиты от раздвоения мозга. Данные целы на всех живых копиях.

**Действие одно: поднять любую одну из упавших нод — кластер оживёт сам.**

- Поднятая нода видит выжившую (или выравнивается с ней) → кворум 2/3
  восстановлен → запись разрешается → вторую ноду лечишь спокойно по §5.
- Что поднимать быстрее: ту, чей диск вероятнее цел (просто ребутнулась,
  отключали питание) — она вернётся перемоткой, без полного клона.
- `--repair` на поднятой ноде — если сама не поднялась в кластер (repmgrd
  стартует сам, но при сомнениях ремонт безвреден и идемпотентен).

**Крайний случай** — обе data-ноды уничтожены физически, остался только
witness: он **не содержит** пользовательских данных. Данные — только в
резервных копиях; восстановление из них — вне этого рунбука (кластер после
восстановления собирается заново по §1).

**Никогда не делай:** ручной promote выжившей standby (`pg_ctl promote` при
остановленных repmgrd) при живой или неизвестно-живой второй ноде — это и есть
раздвоение primary. Break-glass-промоушен допустим только при достоверной
гибели обеих остальных нод и с последующей пересборкой кластера с нуля
(DESIGN.md §12.4).

## 7. Обновление скриптов и переход на другую ветку

Когда: в репозитории установщика появились фиксы, или нужно перейти на другую
ветку (например, с `alt` на следующую).

```sh
cd /usr/src/fusionpbx-install.sh
git fetch origin
git status                       # посмотреть, где стоишь и что изменено
git checkout <ветка>             # или: git pull, если уже на нужной ветке
```

**Что происходит:** обновляются **только файлы репозитория** — скрипты и
шаблоны. Не трогается ничего: базы данных, `/etc/fusionpbx`, `/etc/repmgr`,
`/etc/fusionpbx-ha`, `/etc/angie`. Работающий кластер продолжает работать на
существующих конфигурациях. Обновлять репозиторий нужно на всех нодах, где
запускаешь его команды (минимум — там, где будешь запускать `--repair` /
`--status`).

**0.3.34: `fusionpbx-ha.sh` переехал из `Alt/ha/` в `Alt/`** — рядом с
`pre-install.sh`/`install.sh` (одна система — одно место); ресурсы, тесты и
документация остались в `Alt/ha/`. Скрипт сам находит свои ресурсы в обеих
раскладках (и в плоской копии вида `/root/ha/{fusionpbx-ha.sh,resources/}`);
команды запускаются из `Alt/`. Если в твоём локальном клоне файл уже
перемещён руками и `git pull` конфликтует на переименовании — выполни
`git checkout -- Alt/ha/fusionpbx-ha.sh` (или `git stash`) и повтори pull.
После обновления на живом кластере 0.3.33 → 0.3.34 прогони `--repair` на
всех трёх нодах (сходится `.pgpass`, см. §5) и проверь `--doctor`.

**0.3.34 → 0.3.35 на живом кластере** (закрывает sudo-дыру промоута и
зомби-остаток авто-rejoin): `git pull` ×3 → `--repair` на всех трёх
(сходится юнит-дроп-ин repmgrd с `NoNewPrivileges=no`, верификация
sudo-пути для перезапуска приложений и новый promote.sh с абсолютным
путём) → `--doctor` ×3. Если в repmgrd.log повышенной ноды есть
«could not restart» — см. §3б (приложения перезапусти руками).

**Применять ли новые шаблоны:** повторный запуск слоя 1 на живой системе
guard отклонит (это защита, см. README корня). Применение обновлений к
установленной системе — отдельная процедура; без необходимости не запускать.
HA-слой после обновления файлов просто проверяется: `--doctor` на data-нодах.

**Обновление самой FusionPBX** (ядро приложения, не скрипты) — через веб-интерфейс
(Advanced → Upgrade на текущей primary). Помнить главное: web-дерево
(`/var/www/fusionpbx`) **не синхронизируется** между нодами — обновлять на
каждой data-ноде отдельно; схема БД обновляется один раз (она общая). Полная
процедура апгрейда нод (со switchover) — в будущих расширениях (DESIGN.md
§17); до её появления апгрейд мажора PostgreSQL на живом кластере не
производить.

## 8. Работа за HTTP(S)-прокси

Весь исходящий интернет (пакеты, репозитории) может ходить только через
корпоративный прокси — это поддерживается на всех уровнях тем же флагом, что и
в слое 1. Межнодовый трафик кластера (репликация, rsync, haproxy-проверки)
идёт напрямую и прокси не касается; скрипт сам исключает адреса кластера из
прокси (`no_proxy`), отдельная настройка не нужна.

**Первый заход на чистую машину** (прокси ещё нигде не прописан) — перед
клонированием репозитория:

```sh
export http_proxy=http://<proxy-host>:<port> https_proxy=$http_proxy
git clone -b alt https://github.com/sw-alex-1/fusionpbx-install.sh.git
```

**Слой 1** (VM1, VM2) — свой флаг, см. README корня:

```sh
./pre-install.sh --proxy <proxy-host>:<port>
./install.sh --proxy <proxy-host>:<port>
```

**HA-скрипт** — тот же флаг на любой команде:

```sh
./fusionpbx-ha.sh --init --node2 <IP> --node3 <IP> --proxy <proxy-host>:<port>
./fusionpbx-ha.sh --join <ТОКЕН> --proxy <proxy-host>:<port>   # особенно VM3: там слоя 1 не было
```

**Что происходит:** прокси прописывается во все потребители (APT, git, wget,
curl) персистентно. На второй и последующие разы (`--repair`, `--status`)
флаг на той же ноде уже не обязателен — но и не вреден.

## 9. Логи и точки входа для диагностики

| Что смотреть | Где |
|---|---|
| События кластера, failover, promote | `/var/log/repmgr/repmgrd.log` — ГЛАВНЫЙ источник по repmgrd: после строки `redirecting logging output` ВСЯ диагностика демона уходит туда, `journalctl -u repmgr` бесполезен (0.3.15) |
| «Another instance of rrsync is already accessing this directory» | rrsync (rsync 3.2.7) берёт эксклюзивный flock на сам каталог стека: на указанной ноде живёт (завис) другой его экземпляр — остаток прерванной сессии синка (жёсткие выключения, рестарты lsyncd на середине передачи). Всё медиа-синхро до/с этой ноды стоит, пока жив процесс. Диагноз: `ps ax | grep rrsync` на этой ноде + `--doctor` (проверка 8d, 0.3.23). Лечение: убить зависший процесс (`kill <PID>`) — блокировка умирает вместе с процессом; seed при ремонте сам ждёт и повторяет (5×15с) |
| Причина смерти repmgrd при старте | `tail -n 20 /var/log/repmgr/repmgrd.log`; типовое: `unable to write to shared memory` = нет `shared_preload_libraries='repmgr'` → `./fusionpbx-ha.sh --doctor` подскажет чин-команду по роли ноды: primary `--init --force`, standby `--repair --force-clone`, witness `--repair` (0.3.16: doctor сам конфиги не пишет) |
| Состояние кластера одной командой | `repmgr cluster show` (под postgres) |
